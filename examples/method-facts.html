Method facts

A guest opens a booking, then confirms it or cancels it. A payment from an outside system becomes a deposit.

The model states facts that earlier versions kept in descriptions, comments, or hotspots. Spec v0.8.0 added these facts. The model uses every new construct of v0.8.0.

What the model shows

  • Aggregate identity. identity = field_type.booking_id on the booking aggregate names the field type of one stream. Each event of the aggregate has a booking_id field. Without it, the event is EM018.
  • Key flags. The outside event payment_received marks booking_reference with correlation_key = true and payment_reference with deduplication_key = true.
  • Lifecycle. The booking lifecycle has the states open, confirmed, and canceled. Three transitions move a stream between them. before = [] on open_booking states that this transition starts the stream. The invalid transition confirm_canceled_booking states that a canceled booking cannot be confirmed.
  • Field sources. Each field_source states where one field gets its value, for example command.open_booking.field.guest_name from screen.booking_form.field.name. The input and the target connect along one canonical edge of the workflow.
  • Scenario cases. case names the business rule of each scenario: happy_path, state_violation, and business_duplicate for command scenarios, and appear and disappear for read model scenarios.
  • Empty history. The scenario no_booking_yet has empty_history = true. It states the open bookings list before any event.
  • Dispatch assertions. In record_deposit, the scenario payment_becomes_deposit states that the processor issues record_deposit. The scenario repeated_payment_is_ignored states with expect_no_dispatch = true that a repeated payment issues no command.
  • Evidence. The evidence source booking_policy is a document. One evidence record with certainty = "stated" supports the invalid transition. Another record with certainty = "assumed" states that no source says that a payment reference is unique.
  • Decision. one_open_bookings_list accepts the EM403 signal on the open bookings read model and gives the reason. The signal stays. The decision does not change a diagnostic.
  • Hotspot kinds. refund_rule is an assumption about a rule, with two answer options. late_cancellation_scenario is a request that concerns a scenario.

emhcl export drops these facts with a warning, because Event Modeling JSON cannot hold them.
