Scenarios: make the slice testable

A scenario sits beside its workflow. It describes one business rule with typed steps.

WorkflowGivenWhenThenCardinality
State ChangeEventCommandEvent or Errorzero or more given, one when, one or more then
State ViewEventnoneRead Model or Errorone or more given, or zero with empty_history = true, zero when, one or more then
Automation, action formEvent or Read ModelProcessor or CommandEvent or Error, and Command when the when step targets a Processorzero or more given, one when, one or more then
Automation, view formEventnoneRead Model of the same Automation, or Errorone or more given, or zero with empty_history = true, zero when, one or more then

Each step has one typed target. An error target contains a literal string.

The v0.8.0 specification defines these HCL rules. Canvas examples in the methodology are conceptual, not alternative grammar. A Translation is an automation, so the Automation rules apply to it.

State Change scenario

Given Event(s) When Command Then Event or Error board { workflows = [workflow.add_pet] } bounded_context "owner_management" { event "owner_registered" { } } bounded_context "pet_management" { event "pet_added" { } } state_change "add_pet" { screen "add_pet_ui" { to = [command.add_pet_command] } command "add_pet_command" { to = [event.pet_management.pet_added] } scenario "add_pet_success" { given { event = event.owner_management.owner_registered } when { command = command.add_pet_command } then { event = event.pet_management.pet_added } } }

An error path uses a different then target. An optional comment records the business rule:

board { workflows = [workflow.add_pet] } bounded_context "pet_management" { event "pet_added" { } } state_change "add_pet" { screen "add_pet_ui" { to = [command.add_pet_command] } command "add_pet_command" { to = [event.pet_management.pet_added] } scenario "add_pet_validation_error" { when { command = command.add_pet_command } then { error = "Pet name is required" } comment { description = "A pet must have a name before it can be registered." } } }

State View scenario

Given Event(s) Then Read Model or Error

For example: given Student Registered, then Students to Welcome.

board { workflows = [workflow.welcome_students] } bounded_context "students" { event "student_registered" { } } state_view "welcome_students" { readmodel "students_to_welcome" { question = "Which registered students still need a welcome?" from = [event.students.student_registered] } scenario "registered_student_needs_welcome" { given { event = event.students.student_registered } then { readmodel = readmodel.students_to_welcome } } }

A State View has one or more Event given steps, no when, and one or more Read Model or Error then steps. The only exception is a scenario with empty_history = true, which has no given step. See Empty history.

If you work from an older draft, read the migration guide for the removed Query form.

Automation scenarios

An Automation scenario has two forms. The number of when steps selects the form. A Translation is an Automation, so it uses the same two forms.

An action form scenario has one when step. It states what follows when the Processor or the Command acts. The given step targets an Event or Read Model. The when step targets a Processor or Command. The then step targets an Event or Error. If the when step targets a Processor, a then step can also target a Command. See Dispatch assertions.

board { workflows = [workflow.add_weather_forecast] } bounded_context "appointments" { event "appointment_added" { } } bounded_context "weather" { event "weather_predicted_for_appointment" { } } automation "add_weather_forecast" { readmodel "appointments_without_weather_forecast" { question = "Which appointments still need a weather forecast?" description = "Appointment Added adds pending work. Weather Predicted for Appointment removes the matching item." from = [event.appointments.appointment_added, event.weather.weather_predicted_for_appointment] to = [processor.weather_processor] } processor "weather_processor" { to = [command.add_weather_forecast] } command "add_weather_forecast" { to = [event.weather.weather_predicted_for_appointment] } scenario "forecast_is_added" { given { event = event.appointments.appointment_added } when { processor = processor.weather_processor } then { event = event.weather.weather_predicted_for_appointment } } }

A view form scenario has no when step. It states the content of a Read Model of the same Automation after the given Events. It does not run the Processor and does not issue a Command. Use it to specify the todo list. Set expect_empty_list = true to state that the list is empty.

board { workflows = [workflow.add_weather_forecast] } bounded_context "appointments" { event "appointment_added" { } } bounded_context "weather" { event "weather_predicted_for_appointment" { } } automation "add_weather_forecast" { readmodel "appointments_without_weather_forecast" { question = "Which appointments still need a weather forecast?" from = [event.appointments.appointment_added, event.weather.weather_predicted_for_appointment] to = [processor.weather_processor] } processor "weather_processor" { to = [command.add_weather_forecast] } command "add_weather_forecast" { to = [event.weather.weather_predicted_for_appointment] } scenario "new_appointment_needs_forecast" { given { event = event.appointments.appointment_added } then { readmodel = readmodel.appointments_without_weather_forecast } } scenario "forecast_removes_appointment_from_list" { given { event = event.appointments.appointment_added } given { event = event.weather.weather_predicted_for_appointment } then { expect_empty_list = true readmodel = readmodel.appointments_without_weather_forecast } } }

Scenario cases

The optional case attribute states the kind of business rule that one scenario covers. A reader or a coverage tool can then count the cases of each Command and each Read Model.

board { workflows = [workflow.confirm_booking] } bounded_context "booking" { event "booking_opened" { } event "booking_canceled" { } event "booking_confirmed" { } } state_change "confirm_booking" { screen "booking_details" { to = [command.confirm_booking] } command "confirm_booking" { to = [event.booking.booking_confirmed] } scenario "open_booking_is_confirmed" { case = "happy_path" given { event = event.booking.booking_opened } when { command = command.confirm_booking } then { event = event.booking.booking_confirmed } } scenario "canceled_booking_is_not_confirmed" { case = "state_violation" given { event = event.booking.booking_opened } given { event = event.booking.booking_canceled } when { command = command.confirm_booking } then { error = "A canceled booking cannot be confirmed." } } }

The value comes from a closed list with two groups. The form of the scenario selects the group:

GroupScenariosValues
Command casesState Change, Automation action formhappy_path, variant, refused_input, state_violation, business_duplicate, limit, authorization, alternative_path, external_failure, compensation
Read Model casesState View, Automation view formappear, change, disappear

An unknown value is EM008. A value from the wrong group is EM304, for example case = "appear" in a State Change scenario. The validator does not compare the case with the steps. For example, a refused_input scenario does not need an Error step.

Empty history

A Read Model also has a state before any Event. To state it, write empty_history = true and no given step. This works in a State View scenario and in an Automation view form scenario.

board { workflows = [workflow.open_bookings] } bounded_context "booking" { event "booking_opened" { } } state_view "open_bookings" { readmodel "open_bookings" { question = "Which bookings are open?" from = [event.booking.booking_opened] } scenario "no_booking_yet" { empty_history = true then { expect_empty_list = true readmodel = readmodel.open_bookings } } scenario "opened_booking_appears" { case = "appear" given { event = event.booking.booking_opened } then { readmodel = readmodel.open_bookings } } }

A given step together with empty_history = true is EM301. A view scenario without a given step and without empty_history = true is also EM301. On a State Change scenario or an Automation action form scenario, empty_history is EM304. The count of when steps still selects the form of an Automation scenario.

Dispatch assertions

A dispatch is the issue of a Command by a Processor. In an action form scenario whose when step targets a Processor, a then Command step states that the Processor issues that Command. expect_no_dispatch = true states that the Processor does not issue it in this situation.

board { workflows = [workflow.record_deposit] } bounded_context "booking" { event "deposit_recorded" { } } bounded_context "payments" { external = true event "payment_received" { } } automation "record_deposit" { processor "deposit_translator" { from = [event.payments.payment_received] to = [command.record_deposit] } command "record_deposit" { to = [event.booking.deposit_recorded] } scenario "payment_becomes_deposit" { case = "happy_path" given { event = event.payments.payment_received } when { processor = processor.deposit_translator } then { command = command.record_deposit } } scenario "repeated_payment_is_ignored" { case = "business_duplicate" given { event = event.booking.deposit_recorded } given { event = event.payments.payment_received } when { processor = processor.deposit_translator } then { expect_no_dispatch = true command = command.record_deposit } } }

Field blocks on a dispatch step state the values of the issued Command. The rules are:

  • Use the local form command.<id>. A Command of another workflow is EM101.
  • A then Command step in a State Change or State View scenario, or after a when Command, is EM303.
  • expect_no_dispatch on another step, or together with fields on the same step, is EM304.
  • A scenario that both issues and does not issue the same Command is EM305.
  • One scenario can have Event, Error, and Command then steps together.

The validator does not require a to edge from the Processor to the Command. A no-dispatch assertion does not add a possible dispatch path.

Cover behavior, not just syntax

For each Command, review success, invalid input, invalid state, duplicate actions, alternative outcomes, external failure, and compensation. Write each applicable case and name it in case.

Use the actual business thresholds and concrete field values. Explain why a case cannot occur instead of inventing a rule.

Review Read Models separately, including todo lists. Cover the empty start, population, updates, and removal from their source Events.

The methodology also uses storylines for lifecycles. HCL has no storyline block. State the states and transitions of a stream in a lifecycle block. Write a state_violation scenario for each invalid transition.

A canvas automation can describe an empty When and a dispatched Command in Then. Native HCL has no empty When in an action form scenario. Name the Processor in the when step and the dispatched Command in a then step.

Do not invent a query attribute. A rejected Command uses an Error target, not an empty-list assertion. Use expect_empty_list only on a Read Model then step. Record a tracked business failure as an Event.

See methodology scenario coverage for discovery questions. Keep forms that HCL cannot express in explanatory prose, not invented syntax.
