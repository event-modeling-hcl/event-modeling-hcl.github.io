The language

How documents, identities, references, fields, and flow work.

The model

A model contains domain catalogs (lists of shared definitions), one board, workshop notation, and workflows. Catalogs define contexts, actors, ownership, Events, aggregates, and field types. Workflows describe behavior. Chapters and hotspots keep workshop context.

Specification v0.7.0 defines a model as one .em.hcl file or a folder of member files. A folder includes only direct .em.hcl files whose names do not start with a dot. It does not include subfolders.

Each file holds whole top-level blocks and must parse on its own. References resolve across member files without changing ID scopes. A block never spans files, so each bounded context and its domain contracts stay in one file. File names and block order have no meaning. If you move blocks between files, the model does not change. See Folder models.

After validation, downstream tools use a normalized typed model that has literal titles and source-to-target edges.

The board sets the story order

A model has exactly one top-level board block. Its workflows list is the complete story order for diagrams:

board { workflows = [workflow.add_pet] } state_change "add_pet" { }

A missing or repeated board is error EM015. A repeated entry in the list is error EM016. The list can omit workflows. An omitted workflow is off-board. It stays part of the model and passes every rule, but it is not in the story order.

Chapters are membership sets. A chapter lists its workflows, but it does not set order. A workflow in two chapters is error EM014. An empty chapter is error EM005.

Identities and literal titles

In the block above, the identity is add_pet. Labels use lower_snake_case. A title is a literal string. If you omit title, the model has no title. Tools never derive a title from the label. A tool can show the identity instead.

board { workflows = [] } bounded_context "billing" { event "payment_failed" { title = "Card Payment Was Declined" } }

The formatter never writes a title and formats one file at a time.

Typed references

Quoted values are data. Unquoted traversals are references. For example, to = [event.pet_management.pet_added] resolves a relationship. If you quote that traversal, it becomes an invalid string.

Bounded contexts own domain contracts

Events, aggregates, and field types belong to a bounded context:

board { workflows = [] } bounded_context "pet_management" { aggregate "pet" { } field_type "pet_id" { type = "Int" id_attribute = true example = 5 } event "pet_added" { aggregate = aggregate.pet field "pet_id" { type = field_type.pet_id } } }

Inside the owning context, references are local, for example aggregate.pet and field_type.pet_id. Outside the context, use the qualified form: aggregate.pet_management.pet, field_type.pet_management.pet_id, event.pet_management.pet_added.

Aggregates

An aggregate is a consistency boundary that a context owns:

board { workflows = [] } bounded_context "pet_management" { aggregate "pet" { title = "Pet" description = "Consistency boundary for pet details." } }

Use aggregate_dependencies when behavior spans another consistency boundary.

Reusable field types

Use a field_type when the same business term appears in several contracts:

board { workflows = [] } bounded_context "owner_management" { field_type "owner_id" { type = "Int" example = 42 id_attribute = true } event "owner_registered" { field "owner_id" { type = field_type.owner_id } } }

For a one-off field, write a built-in type inline, for example field "request_id" { type = "UUID" }. The reference lists the available types and flags.

The fields list

Every field and subfield must set type. A missing type is error EM009. The language never infers a type from the field name. A fields list adds several typed fields at once. Each entry adds one field, named for the last part of the reference:

board { workflows = [] } bounded_context "pet_management" { field_type "pet_id" { type = "UUID" } field_type "pet_name" { type = "String" } event "pet_added" { fields = [field_type.pet_id] field "pet_name" { type = field_type.pet_name } } }

The list takes no per-field overrides. Use a field block for those. A field_type must declare a built-in type.

Lists and structured data

A custom reusable field type can carry nested subfields:

board { workflows = [] } bounded_context "owner_management" { field_type "owner_pets" { type = "Custom" cardinality = "List" example = [{ id = 5 name = "Mochi" birthDate = "2020-01-12" }] subfield "id" { type = "Int" id_attribute = true } subfield "name" { type = "String" } } }

Examples are native HCL literals. The validator checks that examples match the effective type.

One edge, one canonical declaration

Each edge has one canonical spelling.

Rule 1, workflow-local source: write to on the source.

board { workflows = [workflow.add_pet] } bounded_context "pet_management" { event "pet_added" { } } state_change "add_pet" { screen "add_pet_form" { to = [command.add_pet] } command "add_pet" { to = [event.pet_management.pet_added] } }

Rule 2, catalog Event source: write from on the receiving workflow element.

Here is what happens if a Command reverses the first rule. The Command puts from on itself instead of to on the Screen:

board { workflows = [workflow.create_pet] } bounded_context "example" { event "pet_created" { } } state_change "create_pet" { screen "form" { to = [command.create] } command "create" { from = [screen.form] to = [event.example.pet_created] } }

The validator rejects the reverse form:

reverse-flow.em.hcl:16:13: Error EM201: Invalid flow reference: command.from has no canonical flow targets in a state_change workflow. You referenced: screen.form.

To check an edge, find the source. Use to on a workflow source. Use from on the receiver if the source is a catalog Event.
