The language

The mechanics beneath the four patterns: what a document contains, how identity and titles work, and the one habit — typed references — that matters more than any other.

The document model

A .em.hcl file contains three broad categories. Catalog declarations — bounded_context, actor, team, system, and inside a bounded context aggregate, field_type, event — describe the domain. Workshop notation — chapter, hotspot — carries facilitation state. Workflows — state_change, state_view, automation, translation — describe behavior. A current model is one .em.hcl document.

.em.hcl is the authoring syntax. After validation, downstream tooling reads the normalized typed model — internal/model.Load — rather than raw HCL. That model exposes effective derived titles and a canonical source-to-target edge list, and it separates semantic data (aggregate, from, to, question, actor) from presentation metadata (group_id, tags, sketched).

Identities and derived titles

state_change "add_pet" { }

Identity is add_pet; effective display title is Add Pet — title-cased from the label automatically. Labels use lower_snake_case. Do not repeat identity using id, name, type, or an index attribute. Write an explicit title only when you want different wording:

bounded_context "billing" { event "payment_failed" { title = "Card Payment Was Declined" } }

The formatter does not write derived titles back into source — required semantic data like readmodel.question, actor.auth_required, field type, and hotspot question stays required regardless. Source order is model order, too: no index or spec_row bookkeeping. Keep workflows in business-time order so the file reads like the Event Model, left to right.

Typed references: the most important syntax habit

The language deliberately distinguishes literal data from relationships. Quoted values are data, like description = "Registers a new pet.". Unquoted traversals are references, like to = [event.pet_management.pet_added] or actor = actor.clinic_staff. Do not do this — to = ["event.pet_management.pet_added"] is a quoted string, not a reference, and will not resolve.

Bounded contexts own domain contracts

Events, aggregates, and field types belong to a bounded context:

bounded_context "pet_management" { aggregate "pet" { } field_type "pet_id" { type = "Int" id_attribute = true example = 5 } event "pet_added" { aggregate = aggregate.pet field "pet_id" { type = field_type.pet_id } } }

Inside the owning context, references are local: aggregate.pet, field_type.pet_id. Outside it, use the qualified form: aggregate.pet_management.pet, field_type.pet_management.pet_id, event.pet_management.pet_added.

Aggregates

An aggregate is a context-owned consistency boundary. title and description are optional:

bounded_context "pet_management" { aggregate "pet" { title = "Pet" description = "Consistency boundary for pet details." } }

Commands and Events may declare aggregate dependencies when behavior spans another consistency boundary, with aggregate_dependencies = [aggregate.owner_management.owner]. Aggregates are not a substitute for Event Modeling — the behavior timeline still comes first.

Reusable field types

Use a field_type when the same ubiquitous-language concept appears in multiple contracts:

bounded_context "owner_management" { field_type "owner_id" { type = "Int" example = 42 id_attribute = true } event "owner_registered" { field "owner_id" { type = field_type.owner_id } } }

For one-off technical data, a built-in type can be inline instead: field "request_id" { type = "UUID" }. Supported built-in types in v0.2.0 are String, Boolean, Double, Decimal, Long, Custom, Date, DateTime, UUID, and Int. Fields are required by default — set optional = true only when absence is genuinely valid, and pii = true for personally identifiable information.

Lists and structured data

A custom reusable field type can carry nested subfields:

bounded_context "owner_management" { field_type "owner_pets" { type = "Custom" cardinality = "List" example = [{ id = 5 name = "Mochi" birthDate = "2020-01-12" }] subfield "id" { type = "Int" id_attribute = true } subfield "name" { type = "String" } } }

Examples are native HCL literals, and the validator checks that examples match the effective type.

One edge, one canonical declaration

The schema does not let you choose either endpoint for an edge — each has exactly one canonical spelling. This removes ambiguity for humans, diffs, formatters, and LLM generation.

Rule 1 — workflow-local source: write to on the source.

bounded_context "pet_management" { event "pet_added" { } } state_change "add_pet" { screen "add_pet_form" { to = [command.add_pet] } command "add_pet" { to = [event.pet_management.pet_added] } }

Rule 2 — catalog Event source: write from on the receiver. Catalog Events carry no workflow-specific edges themselves, so the receiving element records the incoming relationship — this is exactly the pattern every readmodel.from you've seen on this page uses.

Here is what happens when a Command reverses the first rule and puts from on itself instead of to on the Screen:

bounded_context "example" { event "pet_created" { } } state_change "create_pet" { screen "form" { to = [command.create] } command "create" { from = [screen.form] to = [event.example.pet_created] } }

That's a real fixture from the validator's own test suite. Running it produces a genuine rejection, not a hypothetical one:

reverse-flow.em.hcl:11:13: Error EM201: Invalid flow reference: command.from has no canonical flow targets in a state_change workflow. You referenced: screen.form.

Retrieval rule: when unsure where an edge goes, ask who is the source? If the source is a workflow element, put to on it. If the source is a catalog Event, put from on the receiving workflow element.
