Quality: smells, errors, and warnings

The validator checks structure. Business clarity still requires judgment.

The four anti-patterns

These shapes are warnings. Investigate them. The validator does not reject them automatically.

Left chair

1 Command → many Events. Check whether several business capabilities are mixed together.

Right chair

many Events → 1 Read Model. Check whether the Read Model answers more than one question.

Bed

1 Screen → many Commands. Split any second action into another Screen state, even when the intents are related.

Shelf

1 workflow → many scenarios, others → none. Check which workflows still rely on implicit rules.

ShelfEM405: at least two scenarios, all in one workflow, with another workflow presentNoticeably more scenarios than neighboring workflows. No fixed count.

Chair and shelf counts start a review, not an automatic split. Inspect the actual rules and fields. Explain justified fan-in or fan-out.

Use plain business language with stakeholders. The shape nicknames are internal shorthand.

What the validator rejects outright

All profiles reject these core problems: invalid HCL and unknown syntax, missing required semantic attributes, wrong literal types, invalid examples, duplicate identities, unresolved references, and references of the wrong kind. They also reject a missing or repeated board (EM015), a workflow listed twice on the board (EM016), and a field without a valid type (EM009). Other core problems are non-canonical flow directions, invalid pattern-specific scenario structure, an empty chapter (EM005), and a workflow in two chapters (EM014). File layout and block order have no meaning. A workflow that is not on the board is valid. Diagnostics use stable EMxxx codes. EM0xx codes report structure, EM1xx references, EM2xx flow, EM3xx scenarios, and EM4xx modeling judgment. The codes EM006, EM011, EM012, EM013, and EM407 are retired.

What it leaves to human judgment

Some checks need judgment, not hard rejection. These are a Command with no incoming flow and no external_trigger (EM404), the four anti-patterns above, and an open hotspot (EM406). An api_endpoint on a Command does not give it a reason. If a client sends the Command through an API, add an API screen that flows to it. Three profiles set the severity of these checks. A profile never decides whether tools get the model. A tool that renders or exports still gets the typed model when only a profile rejects it.

This Command has no incoming flow and no trigger:

board { workflows = [workflow.schedule_appointment] } bounded_context "appointments" { event "appointment_added" { } } state_change "schedule_appointment" { command "add_appointment" { to = [event.appointments.appointment_added] } }

Under the default valid profile, this is a warning and the file still validates:

em404-test.em.hcl:11:3: Warning EM404: Every command has a reason: command "add_appointment" has no incoming flow or external_trigger. em404-test.em.hcl valid

Under --profile strict, the same diagnostic becomes a hard error, and the validator reports nothing as valid:

em404-test.em.hcl:11:3: Error EM404: Every command has a reason: command "add_appointment" has no incoming flow or external_trigger.

A shipped example also produces a right-chair warning:

pet-management-detailed.em.hcl:459:12: Warning EM403: Right chair anti-pattern: readmodel "owner_details" connects to several events; review whether the workflow contains more than one business capability. pet-management-detailed.em.hcl valid

To make an agent-ready model more explicit, use strictness. Do not use permissiveness to hide uncertainty. Put unknown business facts in hotspot blocks, not in silence.

Review information completeness

Walk the full business journey, including cancellation, failure, and compensation. Inspect the current fields, connections, and scenarios rather than relying on memory.

  • Trace each Event field to Command input or a documented domain calculation or generated value.
  • Trace each displayed Read Model field to connected Events and explain derived values.
  • Trace each required Command input to its human or machine issuer. Explain inputs that do not reach resulting business state.
  • Review consumer needs, identity, and ownership across context boundaries. Inspect existing sources before declaring data missing.

A passing validator does not prove that these sources or business rules are complete. Keep genuine unknowns as attached hotspot blocks. Do not invent answers to pass strict validation.

Review structure and business meaning separately. Record findings before making changes. A model with a material open question is not implementation-ready.

Respect workflow ownership

HCL workflow statuses are created, planned, assigned, in_progress, review, blocked, done, and informational.

Under the methodology, edit freely only when status is absent or created. Every other status requires explicit permission for the named workflow and proposed changes.

A field rename across a chain can touch locked work. Do not treat permission for one workflow as permission for its neighbors. Editing done work reopens it.

These edit locks are collaboration rules, not a claim that the HCL validator enforces permission.

Validity-spotting drill

For each item, decide which label applies: invalid (a validator-level problem), valid but suspicious (a warning or smell), or valid.

A event "order_placed" { title = "Order Placed" }
Answer

Invalid Events are contracts that a bounded context owns. You must declare them inside a bounded_context.

B to = ["event.orders.order_placed"]
Answer

Invalid Relationships are typed, unquoted HCL traversals. This is a string.

C readmodel "order_summary" { title = "Order Summary" }
Answer

Invalid A readmodel block exists only inside a state_view or automation workflow. Even if you declare it correctly, it needs a concrete question.

D One command -> five semantically unrelated events
Answer

Valid but suspicious This is a left-chair smell. Investigate whether one Command hides several capabilities.

E board { workflows = [workflow.register_pet, workflow.pet_directory, workflow.register_pet] }
Answer

Invalid The board lists register_pet twice. The validator reports EM016. Each workflow can appear on the board at most once.

F translation "translate_payment" { ... }
Answer

Invalid The language has no translation block. The validator reports EM000. Write an automation that consumes an Event of an external = true bounded context. Run emhcl migrate to convert an old v0.4.0 model.

G field "pet_name" { }
Answer

Invalid Every field needs a type. The tool does not guess a type from the name. The validator reports EM009.

H A State Change scenario contains two "when" blocks.
Answer

Invalid A State Change scenario requires one when block that targets a Command.
