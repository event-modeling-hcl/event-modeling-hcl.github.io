Use this loop, not a straight read-through

Each idea works best worked through in this order, not read once and filed away:

  1. Predict — answer the prompt before looking at the example.
  2. Retrieve — write the concept or HCL shape from memory.
  3. Compare — inspect the worked example.
  4. Explain — say why each block and reference exists.
  5. Produce — change the example or build a neighboring one.
  6. Validate — run the HCL validator.
  7. Revisit later — repeat after a delay instead of rereading immediately.

If you learned an earlier draft, retrieve these before continuing: flows now have one canonical spelling per edge (reverse forms are invalid); a State View scenario is Given → Then, with no when and no query concept at all; obvious titles are derived from the label, so most examples omit them; validation has profiles (workshop / valid / strict) and stable EMxxx diagnostics; and a canonical fmt command formats source, while downstream tooling reads the validated typed model, not raw HCL.

The six workshop stages, and where each lands in HCL

The workshop is a progression from discovery to testable rules. Two anchor questions carry you through discovery: what is the first Event? What is the last Event? — and, at every step, what happens next?

Workshop mode and authoring mode are different

Do not let the precision of HCL pull implementation detail back into the discovery workshop too early.

Workshop mode

Optimize for shared understanding: start with Events, talk about facts and intent rather than frameworks, avoid polishing diagrams, keep slices small, park uncertainty as a hotspot, and avoid implementation arguments unless they affect business behavior.

Authoring mode

Now become precise: identify bounded-context ownership, give contracts stable identities, add fields and reusable field types, add typed references, make every Read Model answer a concrete question, encode scenarios, and validate the file.
