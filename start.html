Get started

From install to a published canvas

Five steps, no more than a few minutes: install the CLI, write a model, validate it, render it, and publish it next to the code it specifies.

1 · Install the CLI

Two ways to get eventmodeling-hcl — a published release archive, or building from source with Go 1.25 or newer.

Option A: download a release

curl -LO https://github.com/event-modeling-hcl/eventmodeling-hcl/releases/latest/download/eventmodeling-hcl_0.3.0_linux_amd64.tar.gz curl -LO https://github.com/event-modeling-hcl/eventmodeling-hcl/releases/latest/download/checksums.txt sha256sum -c checksums.txt tar -xzf eventmodeling-hcl_0.3.0_linux_amd64.tar.gz

Swap linux_amd64 for darwin_amd64, darwin_arm64, linux_arm64, windows_amd64, or windows_arm64 as needed, and the version number for whatever the releases page currently lists. With GitHub CLI 2.49.0 or newer, you can also verify the archive was actually produced by this repository's release workflow:

gh attestation verify eventmodeling-hcl_0.3.0_linux_amd64.tar.gz --repo event-modeling-hcl/eventmodeling-hcl

Option B: build from source

git clone https://github.com/event-modeling-hcl/eventmodeling-hcl.git cd eventmodeling-hcl go build -o eventmodeling-hcl ./cmd/eventmodeling-hcl

Either way, confirm it runs:

./eventmodeling-hcl version

2 · Write your first model

Save this as pet.em.hcl. It's the same minimal model used throughout this site — one bounded context, one Event, one State Change workflow:

bounded_context "pet_management" { title = "Pet Management" aggregate "pet" { } field_type "pet_id" { type = "Int" id_attribute = true example = 5 } event "pet_added" { title = "Pet Added" aggregate = aggregate.pet field "pet_id" { type = field_type.pet_id } } } state_change "add_pet" { title = "Add Pet" screen "add_pet_form" { title = "Add Pet Form" to = [command.add_pet_command] } command "add_pet_command" { title = "Add Pet" aggregate = aggregate.pet_management.pet to = [event.pet_management.pet_added] field "pet_id" { type = field_type.pet_management.pet_id } } }

3 · Validate it

./eventmodeling-hcl validate pet.em.hcl

A valid document prints exactly this — verified against this exact file with the real CLI while writing this page:

pet.em.hcl valid

A diagnostic instead would look like file:line:column: Severity EMxxx: message. See the quality page for what's a hard error versus a warning worth a second look.

4 · Render the canvas

./eventmodeling-hcl diagram pet.em.hcl -o pet.html wrote pet.html

pet.html is a single self-contained file — no external dependencies, no build step. Open it directly in a browser.

5 · Publish it next to your code

This is the part that makes .em.hcl different from a diagram tool: the model and its rendered canvas are just files. Commit them beside the code they specify, and host the canvas on the same GitHub or GitLab Pages site that documents your project:

git add pet.em.hcl pet.html git commit -m "Add pet-registration event model" git push

Turn on Pages for the repository (or point an existing Pages site at this path), and the rendered canvas is now living documentation — versioned with the code, reviewed in the same pull requests, never drifting out of sync with a wiki page nobody remembers to update.

Working with an LLM instead of by hand? The same three commands — write, validate, diagram — are the exact feedback loop an agent can run on its own. See Author with AI.
