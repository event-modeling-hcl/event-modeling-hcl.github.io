Reads like the domain, not a data format

Most Event-Modeling-as-code tools store your model as YAML or JSON — formats you interpret through a type or kind field. In .em.hcl, an event block is an Event; a state_change block is the State Change pattern. What you write is what it means.

# Minimal Event Modeling document with context-owned contracts. bounded_context "pet_management" { title = "Pet Management" aggregate "pet" { } field_type "pet_id" { type = "Int" id_attribute = true example = 5 } event "pet_added" { title = "Pet Added" aggregate = aggregate.pet field "pet_id" { type = field_type.pet_id } } } state_change "add_pet" { title = "Add Pet" screen "add_pet_form" { title = "Add Pet Form" to = [command.add_pet_command] } command "add_pet_command" { title = "Add Pet" aggregate = aggregate.pet_management.pet to = [event.pet_management.pet_added] field "pet_id" { type = field_type.pet_management.pet_id } } }

Built around three ideas

In your repo, not a separate tool

A .em.hcl file sits beside the code it specifies and versions with it. eventmodeling-hcl diagram renders it into one self-contained HTML file — commit that, host it on GitHub or GitLab Pages, and the event model is documentation that lives next to the code instead of a wiki page that drifts out of sync.

Written by a human, or drafted by an LLM

The grammar is constrained enough for a language model to generate correctly on the first try, and readable enough for a person to review every line it proposed. The validator is the contract between the two.

Validated, not just drawn

Every reference — event.pet_management.pet_added, aggregate.pet — is a typed HCL traversal, checked for scope, kind, and existence before anything renders. A model that looks right and a model that validates are the same model.

A blueprint a model can build from

.em.hcl is deliberately not a general-purpose format: no variables, no interpolation, no computed references — just blocks, typed traversals, and literals. That makes it easy for an LLM to generate correctly the first time, and just as easy for the validator to catch the times it doesn't.

Why HCL, honestly

We picked HCL over YAML and JSON on purpose, for one reason above the rest: HCL blocks let the domain concept be the syntax, instead of a value inside a generic type field. That's not free, and we're not going to pretend it is — the full dimension-by-dimension scorecard and the honest tradeoffs against emlang, ESDM, and Martin Dilger's Event Modeling Specification are laid out on their own page.
