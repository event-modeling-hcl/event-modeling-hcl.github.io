The case for HCL

Why HCL, honestly

We picked HCL over YAML and JSON on purpose. Here's the reasoning, the architecture it leads to, and the costs we're not going to pretend don't exist.

HCL for authoring, a typed IR for everything else

.em.hcl doesn't try to compete with JSON as a machine interchange format, and it doesn't try to be as terse as YAML. It does one job: let a person or a model author an Event Model that reads like Event Modeling. A validator turns that into a strongly typed, normalized model — internal/model.Load — and everything downstream reads from that, not from the HCL text.

In other words: HCL for authoring, typed IR internally, JSON for interchange. We would not make JSON the primary human-authored representation, and we would not try to make .em.hcl as terse as YAML — its job is to make an Event Model look like Event Modeling when you read the source, not to win on keystrokes.

The same Event, three ways

JSON and YAML represent an Event Modeling concept as data — a value inside a generic type or kind field. HCL lets the concept be the syntax.

{ "type": "event", "name": "pet_registered" }
kind: event name: pet_registered
event "pet_registered" { }

The reader of the JSON or YAML has to interpret an object whose type field happens to equal event. The reader of the HCL sees an event block. That difference compounds: a validator can say "expected an Event reference, found a Command reference" instead of "invalid string", because the grammar — not just the data — knows what kind of thing each reference points to.

Where we're not the only answer

event-modeling-hcl isn't the only Event-Modeling-as-code project, and picking HCL was a tradeoff, not a free win. Here's who else is in this space, and where they're a genuinely better fit.

YAML-based

emlang

A YAML-based Event Modeling toolchain with its own parsing, linting, formatting, diagram generation, and a live editor. If you want the lowest possible adoption cost — a teammate can read a kind: event document with zero language-specific training — emlang's YAML is genuinely easier to onboard than a custom HCL dialect.

YAML-based

ESDM

Event-Sourced Domain Modeling represents each contract as a separate apiVersion/kind YAML manifest, with linting, rendering, and editor/schema integration around it. It's a mature, practical ecosystem — if HCL didn't give us typed traversal references and a single canonical spelling per flow, YAML would be our choice too.

JSON Schema

Martin Dilger's Event Modeling Specification

The domain reference this project natively ports into HCL. Its JSON Schema is the closest thing to a canonical interchange format for Event Modeling today — .em.hcl is designed to complement it, not replace it: author in HCL, export the typed IR to JSON for anything that needs that reference format.

The cost of choosing HCL is real: it's a stricter dialect to learn than YAML, full HCL is more powerful than this project needs (we explicitly reject variables, functions, and interpolation to keep models declarative and inspectable), and the tooling — parser integration, validator, formatter, diagnostics — is ours to build and maintain rather than borrowed from a large existing ecosystem. Given that the downstream goal is a high-confidence specification for software-generating agents, we think that's the right trade — but it is a trade, not a strictly-better choice.
