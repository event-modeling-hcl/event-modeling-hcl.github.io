Human + LLM

A blueprint a model can build from

.em.hcl is deliberately not a general-purpose format: no variables, no interpolation, no computed references — just blocks, typed traversals, and literals. That makes it easy for an LLM to generate correctly the first time, and just as easy for the validator to catch the times it doesn't.

The loop

The same three commands a human runs by hand — write, validate, diagram — are exactly the feedback loop an agent can run on its own, with a machine-checkable diagnostic standing in for a human code reviewer's first pass.

1

Describe the workflow

In plain language: the Events involved, who triggers what, which context owns which fact.

2

The model drafts .em.hcl

A constrained grammar with no dynamic features means there's very little space to generate something that merely looks plausible.

3

validate catches the gaps

Stable EMxxx codes and exact source positions — a diagnostic an agent can act on directly, not prose to interpret.

4

diagram shows the result

A human reviews the actual causal shape — the canvas — not the raw HCL text.

5

Build software from the model

The typed IR (internal/model.Load) is the same validated source an agent reads to generate the rest of the system.

The loop, on a real mistake

Here's a realistic failure mode: a model trained on an earlier draft of this language might still reach for a query step in a State View scenario — that concept existed once and no longer does. Say it drafts this:

bounded_context "example" { event "pet_created" { } } state_view "view_pets" { readmodel "pets" { question = "Which pets exist?" } scenario "loaded" { given { event = event.example.pet_created } when { readmodel = readmodel.pets } then { readmodel = readmodel.pets } } }

Running validate — the exact command an agent would run next — rejects it immediately, with a precise reason instead of a vague failure:

state-view-when.em.hcl:12:24: Error EM303: Invalid scenario target: state_view scenario when steps may use: . You referenced: readmodel. state-view-when.em.hcl:10:3: Error EM301: Invalid scenario: state_view scenarios may not contain when steps. Found: when.

That's specific enough to fix without a human in the loop: drop the when block, keep the given and then. The corrected version — the one actually used on the scenarios page — validates cleanly:

bounded_context "students" { event "student_registered" { } } state_view "welcome_students" { readmodel "students_to_welcome" { question = "Which registered students still need a welcome?" from = [event.students.student_registered] } scenario "registered_student_needs_welcome" { given { event = event.students.student_registered } then { readmodel = readmodel.students_to_welcome } } }

No human had to spot the mistake by reading HCL closely — the validator did, in one pass, with a source position and a stable code.

Prompt patterns worth reusing

  • Draft from a list of facts "Here are the business Events for {domain}: {list}. Draft a valid .em.hcl model: pick the right one of the four patterns for each transition, and add one success and one failure scenario per workflow." Gives the model exactly the input Event Modeling itself starts from — facts, not implementation detail.
  • Fix from a diagnostic "Running eventmodeling-hcl validate on this file produced: {paste the EMxxx diagnostic}. Fix the model to satisfy it without changing the modeled behavior." The diagnostic is the whole prompt — no need to explain the rule in your own words.
  • Generate from the model "Here is a validated .em.hcl workflow: {paste it}. Generate the {command handler / read-model projection / API endpoint} for the {workflow} slice in {language}." The model is the spec; ask for an implementation of one slice at a time, not the whole system at once.
