Reference for .em.hcl v0.8.0 and emhcl v0.17.0

The cheat sheet

Blocks, attributes, values, diagnostics, and commands in one page. Specification v0.8.0 defines the language. emhcl v0.17.0 implements it.

Top-level blocks

BlockCategoryPurpose
boardStoryRequired. One per model, with no label. Its workflows list sets the story order.
bounded_contextCatalogOwns aggregates, field types, and Events. external = true marks contracts outside the modeled system.
actorCatalogA reusable human or system actor. Requires auth_required.
teamCatalogA reusable owning team
systemCatalogA reusable external or internal system
state_changeWorkflowScreen → Command → Event
state_viewWorkflowEvent → Read Model → Screen
automationWorkflowEvent → Read Model or Processor → Command → Event. An automation that consumes an Event of an external context is a translation.
chapterWorkshop notationA named set of workflows. The list order has no meaning. A workflow is in one chapter at most.
hotspotRecordAn open or resolved question, assumption, or request. Its on names one attach target.
lifecycleMethod factThe states of the streams of one aggregate, with state, transition, and invalid_transition blocks
evidence_sourceMethod factOne place that evidence comes from: a document, code, an application, or a person
evidenceRecordA source supports one attach target, with a certainty
decisionRecordOne choice that shapes the model, and its reason

The language has no translation block. The block order and the file layout have no meaning. Only the board sets the story order. A workflow that the board does not list is off-board. It is valid and gets no diagnostic. A record (hotspot, evidence, or decision) describes the model and adds no behavior.

Canonical flow

WorkflowEdge spellings

The source element uses to. A catalog Event flows through the from list of the receiver. The reverse spellings produce EM201.

The number of when steps selects the form of an automation scenario. A view form scenario states the content of a read model, for example a to-do list. expect_empty_list = true on a then step states that the read model is empty.

Scenario attributes

AttributeWhereMeaning
case = "..."Any scenarioThe kind of business rule that the scenario states. The form of the scenario selects the group of values. A value from the wrong group is EM304.
empty_history = trueState View scenario, automation view form scenarioThe read model before any event. The scenario has no given step. A given step is EM301. On another scenario, it is EM304.
expect_no_dispatch = truethen command stepThe processor does not issue this command. On another step, or with fields, it is EM304.
GroupScenario formsValues of case
Command casesstate_change, automation action formhappy_path, variant, refused_input, state_violation, business_duplicate, limit, authorization, alternative_path, external_failure, compensation
Read model casesstate_view, automation view formappear, change, disappear

An unknown case is EM008. The tool does not infer a case from the steps and does not compare the case with the steps.

A dispatch is the issue of a command by a processor. A then command step is allowed only in an automation action form scenario whose one when step targets a processor. Elsewhere it is EM303. Use the local form command.<id>. A command of another workflow is EM101. Two then steps that name the same command, with expect_no_dispatch = true on only one of them, are EM305. The tool does not require an edge from the processor to the command.

References are HCL traversals, not strings. Each reference is an exact lookup. Interpolation, functions, and variables are invalid. state.<id> outside a lifecycle is EM101. A field reference names a field definition, also inside a list item. An index step such as x[0] in a field reference is EM101. A field name that the lookup does not find is EM102.

Attach targets

The on of a record names one attach target. All three records accept a catalog item, a workflow, an owner, an actor, a workflow-qualified element, a lifecycle part, and a field reference. A hotspot and an evidence also accept decision.<id>. Only an evidence accepts hotspot.<id>. Another target kind is EM101.

Fields, types, and flags

Every field and subfield requires type. A missing or invalid type is EM009. The tool does not infer a type from a field name. The value is a built-in type string or a field_type reference: field_type.<context>.<id>, or field_type.<id> inside the owning context.

Built-in types: String, Boolean, Double, Decimal, Long, Custom, Date, DateTime, UUID, Int.

fields = [field_type.clinic.pet_id, field_type.clinic.pet_name] adds one typed field for each entry, named for the last part of the reference. The list takes no per-field overrides. Use a field block for those.

AttributeMeaning
type = ...Required. A built-in type string or a field_type reference
id_attribute = trueThis field identifies the record
optional = trueThe field can be absent (fields are required by default)
pii = truePersonally identifiable information
cardinality = "Single" or "List"The field holds one value or a list
example = ...A native HCL literal, checked against the effective type and cardinality (EM010)
correlation_key = trueThe value links an outside fact to an entity of the modeled system
deduplication_key = trueA second delivery with the same value records no new fact

The two key flags are allowed on field and subfield. On a field_type they are EM000. A value that is not a Boolean is EM007. The tool does not infer a flag from a field name.

Aggregate identity

identity on an aggregate is a field_type reference, in the form field_type.<id> or field_type.<context>.<id>. Another value is EM101. Each event of that aggregate must have a top-level field of the identity type. A field with a built-in type string does not count. An event without such a field is EM018.

Each block also accepts title and description. Another form of aggregate, command, or an events entry is EM101. EM017 reports a lifecycle that is not valid: a second lifecycle for the same aggregate, no state block, an empty required list, one state and command pair in a transition and in an invalid transition, or a transition event of another aggregate. A lifecycle adds no flow edge and no scenario. On a command, creates_aggregate = true states that at least one successful outcome creates a stream.

Field sources

AttributeRequiredValue
targetyesOne field reference
inputsyesNon-empty list of field references
descriptionnoText, for example the rule of a derived value

Use the local form for elements of the same workflow and the qualified form for events. A workflow-qualified element of another workflow is EM101. EM202 reports a field source that is not valid: an empty inputs list, an input that does not reach the target along one canonical edge of the workflow, an event or command field with more than one input, or a second field source with the same target. The tool does not compare types or units, and it does not infer a source from equal names.

Titles

title is optional literal text. When you omit it, the element has no title. The tool does not make a title from the label, and views show the ID instead. An empty string is a title.

Screen kinds

kindMeaning
"ui" (default)A state of a user interface. A person uses it directly.
"api"A request to an API, or a response from an API. A client program calls it.

Another string is EM008. A value that is not a string is EM007. kind on a block other than screen is EM000. An API screen uses the same edges as a UI screen. On an API screen, actor names the actor that calls the API, and api_endpoint is the route. On a command, api_endpoint is not a reason. To give such a command a reason, add an API screen that flows to it:

board { workflows = [workflow.register_pet] } bounded_context "clinic" { event "pet_registered" { field "pet_name" { type = "String" } } } actor "clinic_staff" { auth_required = true } state_change "register_pet" { screen "register_pet_request" { kind = "api" api_endpoint = "POST /pets" actor = actor.clinic_staff to = [command.register_pet] } command "register_pet" { to = [event.clinic.pet_registered] field "pet_name" { type = "String" } } }

The typed model stores the effective kind of each screen in the field screen_kind. A fact that another system reports, such as a payment webhook, is not an API screen. Model it as an Event of an external = true context and translate it with an automation.

Status values

Workflow status: created, planned, assigned, in_progress, review, blocked, done, informational.

Hotspot status: open (default) or resolved. An open hotspot produces EM406. Only status controls EM406.

Hotspot kinds

AttributeValues
kind"question" (default), "assumption", or "request"
category"action", "data", "next", "rule", "example", "view", "who", or "time"
optionsList of non-empty strings: the answers that the author offers
concerns"event", "aggregate", "field_type", "command", "readmodel", "screen", "processor", "scenario", "workflow", "board", "chapter", "actor", "lifecycle", or "field_source"

A question states missing information. An assumption states a gap that the author filled, as a question to confirm. A request states a change in another part of the model. A request requires concerns. Without it, or with concerns on another kind, the hotspot is EM000. An unknown value is EM008.

Validation profiles

ProfileEM401–EM403, EM405EM404, EM406
workshopInformationInformation
valid (default)WarningWarning
strictWarningError

Core diagnostics (EM000 to EM305) are errors in every profile, and they stop the typed model. A profile sets only the severity of the judgment signals EM401 to EM406. When a model has no core errors, the tool builds the typed model in every profile. A strict error still makes validate exit with code 1.

CLI commands

In this table, <model> is a .em.hcl file or a folder of .em.hcl files.

emhcl validate [--profile workshop|valid|strict] [--format text|json] <model>Validates the model. The default profile is valid. A valid model prints <path> valid. --format json writes one object with the keys path, profile, has_errors, has_core_errors, and diagnostics.

Board, chapters, and folder models

A model is one .em.hcl file or a folder of .em.hcl files. One-file models and folder models use the same rules. File names and the position of blocks do not change the meaning of a model. Use a folder when one file becomes too large or when different people own different contexts or workflows.

  • Every model has one board block. A missing or repeated board is EM015. A workflow listed twice on the board is EM016. The board can omit workflows. An omitted workflow is off-board: it is valid, and the diagram lists it separately.
  • A chapter is a set of workflows. Its list order has no meaning. An empty chapter is EM005. A workflow in two chapters is EM014. Chapter blocks can be in any member file. Chapters do not change the board, and the board does not change chapters.
  • Every regular file directly in the folder that ends in .em.hcl and does not start with . is a member file. A symlink to a file counts. The tool ignores subfolders and other files.
  • References resolve across member files. IDs keep their existing scopes, with no file namespace. Duplicate IDs in the same top-level ID space produce EM002. Its detail names the first declaration as file:line:column.
  • Each file must parse on its own. A block cannot span files. A bounded_context with all its events, aggregates, and field types is in one file.
  • A folder with no member file is error EM001. A folder with one member file behaves like that file.

The language has no include or import block, no subfolder members, and no references across folders. The pet clinic example shows one layout. The number prefixes only keep the files in reading order for people:

pet-clinic/ 00-catalog.em.hcl # board, bounded_context, actor, team, system 01-chapters.em.hcl # chapter blocks 10-register-pet.em.hcl # one workflow per file 11-pet-directory.em.hcl 12-notify-owner.em.hcl 13-import-partner-pet.em.hcl 90-hotspots.em.hcl

JSON import and export

emhcl import and emhcl export convert between .em.hcl and slice-based Event Modeling JSON. JSON conversion is a tool feature, not part of the language specification.

  • Both commands check the JSON against the published schema. An error names the JSON path of the fault.
  • Import writes a board that lists every slice in document order. Slice type TRANSLATION becomes an automation.
  • Export writes the board workflows in board order, then the off-board workflows in ID order, with a warning that names them. An automation with an edge from an Event of an external context exports as TRANSLATION.
  • The conversion is not lossless. Export drops chapters, hotspots, teams, systems, read-model questions, external_trigger, and screen kind = "api". Import drops original canvas IDs and field-name spellings. Each command writes a warning for each detail that the other format cannot hold.
  • Export also drops the method facts with a warning: aggregate identity, lifecycles, evidence sources, evidence, decisions, field_source blocks, key flags, and scenario case. It omits an empty_history scenario and a no-dispatch then step. When no then step is left, it omits the scenario.
  • Import accepts a then command in an automation specification whose one when step is a processor.
  • Both commands fail when a workflow or slice has two or more actors. They do not choose an actor for you.
  • If the imported model has validation errors, import still writes the source for repair and exits with code 1.

Diagram views

ViewShows
ModelLeft-to-right Event Model of the selected chapter with screen, processor, model, and event swimlanes and typed flow arrows
CompactSame slices and cards as Model, with one events row. Dashed colored boxes show bounded contexts (pink shows external contexts). The aggregate sticky note sits on top of its event.
StormingEvent Model in Event Storming style: one row per workflow with sticky notes for screens, commands, aggregates, events, automations, and read models
SlidesOne slice per slide for readers who do not know Event Modeling: the screen, the scenarios as Given / When / Then examples, open hotspots, and the elements with their fields

One generated file carries all five views. Model, Compact, Storming, and Slides follow the board order. Off-board workflows are listed separately under Off-board workflows. Chapters are the top-level navigation: a model with several chapters opens an All chapters overview, and the chapter picker and its previous and next arrows switch chapters. A model without chapters shows the whole board in every view. An API screen shows its route instead of a wireframe. The Model view marks a no-dispatch step with the flag expect_no_dispatch. Slides show "Expects that the command is not issued". Status, context, and field-detail options are under Filters. The Model and Storming views support zoom. Zoom with the toolbar, Ctrl/⌘ + scroll, or the +, -, 0, and F keys.
