Reference for .em.hcl v0.7.0 and emhcl v0.16.0

The cheat sheet

Blocks, attributes, values, diagnostics, and commands in one page. Specification v0.7.0 defines the language. emhcl v0.16.0 implements it.

Top-level blocks

BlockCategoryPurpose
boardStoryRequired. One per model, with no label. Its workflows list sets the story order.
bounded_contextCatalogOwns aggregates, field types, and Events. external = true marks contracts outside the modeled system.
actorCatalogA reusable human or system actor. Requires auth_required.
teamCatalogA reusable owning team
systemCatalogA reusable external or internal system
state_changeWorkflowScreen → Command → Event
state_viewWorkflowEvent → Read Model → Screen
automationWorkflowEvent → Read Model or Processor → Command → Event. An automation that consumes an Event of an external context is a translation.
chapterWorkshop notationA named set of workflows. The list order has no meaning. A workflow is in one chapter at most.
hotspotWorkshop notationAn open or resolved question or blocker

The language has no translation block. The block order and the file layout have no meaning. Only the board sets the story order. A workflow that the board does not list is off-board. It is valid and gets no diagnostic.

Canonical flow

WorkflowEdge spellings
state_changescreen.to → command, command.to → event
state_viewevent → readmodel.from, readmodel.to → screen
automationevent → readmodel.from or processor.from, readmodel.to → processor, processor.to → command, command.to → event

The source element uses to. A catalog Event flows through the from list of the receiver. The reverse spellings produce EM201.

References are HCL traversals, not strings. Each reference is an exact lookup. Interpolation, functions, and variables are invalid.

Fields, types, and flags

Every field and subfield requires type. A missing or invalid type is EM009. The tool does not infer a type from a field name. The value is a built-in type string or a field_type reference: field_type.<context>.<id>, or field_type.<id> inside the owning context.

Built-in types: String, Boolean, Double, Decimal, Long, Custom, Date, DateTime, UUID, Int.

fields = [field_type.clinic.pet_id, field_type.clinic.pet_name] adds one typed field for each entry, named for the last part of the reference. The list takes no per-field overrides. Use a field block for those.

AttributeMeaning
type = ...Required. A built-in type string or a field_type reference
id_attribute = trueThis field identifies the record
optional = trueThe field can be absent (fields are required by default)
pii = truePersonally identifiable information
cardinality = "Single" or "List"The field holds one value or a list
example = ...A native HCL literal, checked against the effective type and cardinality (EM010)

Titles

title is optional literal text. When you omit it, the element has no title. The tool does not make a title from the label, and views show the ID instead. An empty string is a title.

Screen kinds

kindMeaning
"ui" (default)A state of a user interface. A person uses it directly.
"api"A request to an API, or a response from an API. A client program calls it.

Another string is EM008. A value that is not a string is EM007. kind on a block other than screen is EM000. An API screen uses the same edges as a UI screen. On an API screen, actor names the actor that calls the API, and api_endpoint is the route. On a command, api_endpoint is not a reason. To give such a command a reason, add an API screen that flows to it:

board { workflows = [workflow.register_pet] } bounded_context "clinic" { event "pet_registered" { field "pet_name" { type = "String" } } } actor "clinic_staff" { auth_required = true } state_change "register_pet" { screen "register_pet_request" { kind = "api" api_endpoint = "POST /pets" actor = actor.clinic_staff to = [command.register_pet] } command "register_pet" { to = [event.clinic.pet_registered] field "pet_name" { type = "String" } } }

The typed model stores the effective kind of each screen in the field screen_kind. A fact that another system reports, such as a payment webhook, is not an API screen. Model it as an Event of an external = true context and translate it with an automation.

Status values

Workflow status: created, planned, assigned, in_progress, review, blocked, done, informational.

Hotspot status: open (default) or resolved. An open hotspot produces EM406.

Validation profiles

ProfileEM401–EM403, EM405EM404, EM406
workshopInformationInformation
valid (default)WarningWarning
strictWarningError

Core diagnostics (EM000 to EM303) are errors in every profile, and they stop the typed model. A profile sets only the severity of the judgment signals EM401 to EM406. When a model has no core errors, the tool builds the typed model in every profile. A strict error still makes validate exit with code 1.

Diagnostics print as file:line:column: Severity EMxxx: Summary: Detail. In a folder model, file is the member file that the diagnostic points to.

CLI commands

In this table, <model> is a .em.hcl file or a folder of .em.hcl files.

CommandDoes
emhcl validate [--profile workshop|valid|strict] [--format text|json] <model>Validates the model. The default profile is valid. A valid model prints <path> valid. --format json writes one object with the keys path, profile, has_errors, has_core_errors, and diagnostics.
emhcl fmt [-w | --check] <model>Canonicalizes whitespace and attribute order. Without a flag, prints the result. -w rewrites only the files that change. --check writes no file, prints each file that needs formatting, and exits with code 1 when there is one. On a folder, formats each member file. A syntax error in any member changes no file.
emhcl migrate [-w] <model>Converts a specification v0.4.0 model to the current language. Adds a board, writes each field type and derived title, and rewrites each translation as automation. Without -w, prints the result. With -w, rewrites the changed files.
emhcl diff [--format text|json] <base> <head>Lists the declarations that a change added, removed, or changed, for example changed workflow.register_pet. Compares the typed models, so a moved block or a new layout gives no line. Exits with code 1 when a model has a core error.
emhcl diagram [--title <text>] <model> -o <file>Renders a self-contained interactive HTML canvas with chapter navigation and Model, Compact, Storming, Slides, and Context Map views. Without -o, writes to stdout. --title sets the page title. Core errors stop the output. Modeling judgment does not.
emhcl serve [--addr <host>] [--port <n>] [--profile <p>] <model>Serves the canvas on 127.0.0.1:8080 and reloads when the model changes. For a folder, reloads when you add, remove, rename, or edit a member file. --port 0 picks a free port. With --profile strict, a banner lists the policy errors.
emhcl import <file.json> [-o <model.em.hcl>]Converts Event Modeling JSON to one formatted .em.hcl file and validates it. Without -o, writes to stdout.
emhcl export <model> [-o <file.json>]Converts a valid model to slice-based Event Modeling JSON. Without -o, writes to stdout. Refuses a target that ends in .em.hcl or is the source file (exit code 2).
emhcl version [--format text|json]Prints the installed version, for example emhcl v0.16.0. --format json prints {"tool": ..., "spec": ...}, where spec is the specification version that the tool implements.

Board, chapters, and folder models

A model is one .em.hcl file or a folder of .em.hcl files. One-file models and folder models use the same rules. File names and the position of blocks do not change the meaning of a model. Use a folder when one file becomes too large or when different people own different contexts or workflows.

  • Every model has one board block. A missing or repeated board is EM015. A workflow listed twice on the board is EM016. The board can omit workflows. An omitted workflow is off-board: it is valid, and the diagram lists it separately.
  • A chapter is a set of workflows. Its list order has no meaning. An empty chapter is EM005. A workflow in two chapters is EM014. Chapter blocks can be in any member file. Chapters do not change the board, and the board does not change chapters.
  • Every regular file directly in the folder that ends in .em.hcl and does not start with . is a member file. A symlink to a file counts. The tool ignores subfolders and other files.
  • References resolve across member files. IDs keep their existing scopes, with no file namespace. Duplicate IDs in the same top-level ID space produce EM002. Its detail names the first declaration as file:line:column.
  • Each file must parse on its own. A block cannot span files. A bounded_context with all its events, aggregates, and field types is in one file.
  • A folder with no member file is error EM001. A folder with one member file behaves like that file.

The language has no include or import block, no subfolder members, and no references across folders. The pet clinic example shows one layout. The number prefixes only keep the files in reading order for people:

pet-clinic/ 00-catalog.em.hcl # board, bounded_context, actor, team, system 01-chapters.em.hcl # chapter blocks 10-register-pet.em.hcl # one workflow per file 11-pet-directory.em.hcl 12-notify-owner.em.hcl 13-import-partner-pet.em.hcl 90-hotspots.em.hcl

JSON import and export

emhcl import and emhcl export convert between .em.hcl and slice-based Event Modeling JSON. JSON conversion is a tool feature, not part of the language specification.

  • Both commands check the JSON against the published schema. An error names the JSON path of the fault.
  • Import writes a board that lists every slice in document order. Slice type TRANSLATION becomes an automation.
  • Export writes the board workflows in board order, then the off-board workflows in ID order, with a warning that names them. An automation with an edge from an Event of an external context exports as TRANSLATION.
  • The conversion is not lossless. Export drops chapters, hotspots, teams, systems, read-model questions, external_trigger, and screen kind = "api". Import drops original canvas IDs and field-name spellings. Each command writes a warning for each detail that the other format cannot hold.
  • Both commands fail when a workflow or slice has two or more actors. They do not choose an actor for you.
  • If the imported model has validation errors, import still writes the source for repair and exits with code 1.

Diagram views

ViewShows
ModelLeft-to-right Event Model of the selected chapter with screen, processor, model, and event swimlanes and typed flow arrows
CompactSame slices and cards as Model, with one events row. Dashed colored boxes show bounded contexts (pink shows external contexts). The aggregate sticky note sits on top of its event.
StormingEvent Model in Event Storming style: one row per workflow with sticky notes for screens, commands, aggregates, events, automations, and read models
SlidesOne slice per slide for readers who do not know Event Modeling: the screen, the scenarios as Given / When / Then examples, open hotspots, and the elements with their fields
Context Map (experimental)Whole-model bounded-context map from cross-context event consumption, with upstream and downstream relationships

One generated file carries all five views. Model, Compact, Storming, and Slides follow the board order. Off-board workflows are listed separately under Off-board workflows. Chapters are the top-level navigation: a model with several chapters opens an All chapters overview, and the chapter picker and its previous and next arrows switch chapters. A model without chapters shows the whole board in every view. An API screen shows its route instead of a wireframe. Status, context, and field-detail options are under Filters. The Model and Storming views support zoom. Zoom with the toolbar, Ctrl/⌘ + scroll, or the +, -, 0, and F keys.
